# EPD Toolbox

面向 **E6 六色电子纸**（黑 / 白 / 黄 / 红 / 蓝 / 绿）的静态网页工具箱：图片抖动量化、4bpp 面板数据打包导出、独立的 BLE 设备命令测试页。

纯静态站点，无后端、无构建步骤，推送到 `main` 自动部署到 GitHub Pages；支持 **PWA**，可安装到桌面 / 主屏幕并离线打开。

## 功能

| 页面 | 说明 |
| --- | --- |
| `index.html` | 工具箱首页：工具入口、像素编码与 BLE 帧格式速查 |
| `e6-image.html` | 图像输入 → 抖动量化 → 预览 → 导出 bin / C 数组 → 直接送图 / 刷图 |
| `ble-console.html` | BLE 命令测试：读版本、刷纯色（六色）、刷图、擦除 / 送图图片槽 |

图像页已实现：

- **两套六色色板可选**：`E6 标准色`（000000 / FFFFFF / FFE600 / E8332A / 1B57C4 / 1F9D55）与
  `E6 深色板`（000008 / EFFFFF / FFD700 / 860000 / 001C8A / 145D14）；
  抖动 / 量化按**当前选中色板的 RGB** 计算，写入像素的设备 id 不变（黑0 白1 黄2 红3 蓝5 绿6）
- 12 种抖动算法（Floyd-Steinberg、Atkinson、Jarvis、Stucki、Burkes、Sierra、Sierra Lite、Ordered 2/4/8、阈值、随机）
- 亮度 / 对比度 / 抖动强度 / 蛇形扫描参数
- 尺寸适配：等比留白、等比裁剪、拉伸；分辨率可自定义（默认 480×720）
- 实时 6 色预览（适应 / 1× / 2× / 4× 缩放）与颜色占比统计
- 不做上下翻转：面板方向的反转由固件在刷屏时完成，上位机按正常方向量化 / 打包，
  预览、导出、送图三者的方向完全一致（见 [docs/conventions.md](docs/conventions.md) §12）
- 导出 `.bin`、C 数组 `.h`、复制全部 hex
- 直接连设备**送图**（`0x30`）与**刷图**（`0x11`），两条命令共用一个槽位下拉框（见下文）
- 顶栏连接入口沿用命令测试页的写法：状态徽章（设备名显示在「已连接」左边）、
  连接 / 断开、跳转命令测试页；**名称前缀过滤框**（默认 `EPD`，留空列出全部设备）
  放在页面标题右侧，不占顶栏宽度

命令测试页已实现（对应固件 `CHAR3_CMD_t`）：

| 命令 | 名称 | 可调参数 |
| --- | --- | --- |
| `0x00` | `CHAR3_CMD_00_REVISION` | 无，响应回 3 字节 IC 版本 |
| `0x01` | `CHAR3_CMD_01_TEMPERATURE` | 无，响应回 1 字节温度寄存器原值，页面按 8 位有符号换算成 ℃ |
| `0x10` | `CHAR3_CMD_10_UPDATE_COLOR` | 六色可选（黑 / 白 / 黄 / 红 / 蓝 / 绿） |
| `0x11` | `CHAR3_CMD_11_UPDATE_IMAGE` | 槽号 0~10，把该槽已写好的图刷到屏上 |
| `0x20` | `CHAR3_CMD_20_FLASH_ERASE` | 槽号 0~10，执行前二次确认 |
| `0x30` | `CHAR3_CMD_30_WRITE_IMAGE` | 测试送图：先擦除同槽，再按 233 字节分片写 742 片 |

`0x00` / `0x01` 合并在同一张「读取 IC 信息」卡片里，两个按钮各自独立执行。
温度换算：`TS[7:0]` 是 8 位有符号，`0x00~0x32` = 0~50 ℃、`0xE7~0xFF` = -25~-1 ℃，
其它编码超出规格，页面标「越界」但仍显示有符号解析值（`ble.js` 的 `decodeTemperature()`）。

送图测试卡片的流程（对应 `BLE_Protocol.md` §5）：

1. 生成 480×720 的**六色棋盘图**（60px 方格），按 4bpp 打包成 172800 字节；
2. 目标槽在送图卡片里**独立选择**（0~10，与擦除卡片的槽号互不影响）；
3. 先发 `0x20` 擦除目标槽并等 `0x02`，**擦除失败就不会送图**；
4. 逐片发 `0x30`，offset 从 0 递增 233，每片固定 244 字节帧（最后一片 158 字节），
   **ATT 写响应一回来就发下一片**（成功入队不再回 `DOING`，不要等 `DONE`）；
5. 742 片发完后还要等所有 `DONE` 到齐才算落盘完成（`DONE` 只更新进度、确认写进 Flash）；
6. 勾选「自动刷图」后，送完接着发 `0x11` 把这一槽刷到屏上（复选框在「中止」右边，默认不勾）；
7. 单片失败（GATT 并发错误 / 设备回 `BUSY` 表示队列满、这一包被丢弃）会自动用**同一个 offset** 重发，
   **每片最多 3 次**，协议错误（无效数据、无效命令）不重试；
8. 进度条显示片数 / 已发百分比 / 落盘百分比 / 速度 / 重试次数，可中途「中止」。

> 244 字节的写需要 ATT MTU ≥ 247，Web Bluetooth 没有主动请求 MTU 的接口，由 Chrome 自动协商。
> FFE3 只支持**带响应写**（`writeValueWithResponse`），连上后可用
> `characteristic.properties.writeWithoutResponse === false` 确认固件已是新版。
> 送图只把数据写进 flash，**要显示到屏上必须再发 `0x11`**（槽里没数据就只会刷出空白）。

图像转换页的「4 · 送图 / 刷图」卡片复用同一套 `ble.js` 逻辑，但把两条命令拆成两个按钮、
**共用一个槽位下拉框**，省得写完一槽还得切回命令测试页；连接设备放在顶部工具条（见下）：

- `送图`（`0x30`）：先 `0x20` 擦除该槽，再逐片写 742 片（数据落盘，**屏上不变**）；
- `刷图`（`0x11`）：把该槽里已经写好的图刷到屏上，不改 Flash 内容；
- **自动刷图**（复选框，默认不勾，在「中止」右边）：勾上后送图写完最后一片会接着发 `0x11`，
  一次点完就显示；不勾则只落盘，之后可以单独点「刷图」；
- 卡片版面：状态与耗时在标题右侧，命令码也在标题里（`0x30 · 0x11`），
  底部只有进度条和速度；片号、重试、完成字节数都写在「5 · 日志」里；
- 送图数据就是当前转换结果，**只有尺寸正好 480 × 720（172800 字节）时送图按钮才可点**，
  其它分辨率只能导出；两个命令同样互斥，执行中除连接外的命令控件全部禁用；
- 连接 / 断开与连接状态徽章不看卡片，和命令测试页一样**放在顶部工具条**，滚到哪儿都能连。

命令测试页每张卡片都会实时显示「发送帧」字节，执行后显示状态与耗时；异步命令（`0x10` / `0x11` / `0x20`）会先回 `0x01`，
其中刷屏期间设备会**持续重复发送 `0x01` 心跳**保活，页面按心跳续命并显示实时耗时与心跳次数，完成后才收到 `0x02`。
`0x30` 例外：成功入队不再回 `0x01`，由 ATT 写响应推进发送、`0x02` 只用来累加「已落盘」进度。

通用：

- 命令执行期间**禁用所有命令交互控件**，完成 / 超时 / 出错后恢复（避免并发下发被固件丢弃）；
  命令测试页与图像转换页都遵循这一条
- 连接状态三态显示（未连接 / 连接中… / 已连接），滚动后顶栏常驻状态徽章
- 移动端适配：单列布局、表单项独占一行、顶栏按钮收成图标、表格横向滚动

> 交互与通信的约定（命令互斥、空闲超时、帧语义、移动端…）见 [docs/conventions.md](docs/conventions.md)，
> 新增页面或命令前请先过一遍。

## 数据格式

E6 面板像素为 **4 bit/像素**，两个像素拼一个字节：

- 颜色编号：黑 `0`、白 `1`、黄 `2`、红 `3`、蓝 `5`、绿 `6`（`4`、`7` 保留）
- 字节排布：`byte = (像素(x, 2y) << 4) | 像素(x, 2y+1)`，即**高半字节是上面那个像素**
- 扫描方向：**列优先**，外层 `x = 0 → w-1`
- 一帧字节数：`w × ceil(h / 2)`，480×720 即 **172800** 字节

自测覆盖了位序、列优先、六色编号、整帧往返，以及 BLE 组帧 / 拆帧 / 读版本与读温度应答 / 温度换算边界 / 刷屏心跳 / `0x11` 完成帧 CMD 兼容：

```bash
node tests/codec.test.mjs
node tests/ble.test.mjs
node tests/pwa.test.mjs
```

## BLE 协议

服务 `FFE0`，下行命令 `FFE3`（写），上行响应 `FFE4`（notify）。

```
55 AA LEN_H LEN_L CMD DATA... CRC 0x0D
LEN = 整帧长度 = DATA 长度 + 7（固件校验 LEN 与实际长度一致）
CRC 固件暂不校验，填 0x00
```

| CMD | 含义 | 请求示例 | 应答 |
| --- | --- | --- | --- |
| `0x00` | 读 IC 版本 | `55 AA 00 08 00 00 00 0D` | `55 AA 00 0A 00 10 84 02 00 0D`，**无响应码**，PAYLOAD 即 3 字节版本号 |
| `0x01` | 读 IC 温度 | `55 AA 00 08 01 00 00 0D` | `55 AA 00 08 01 TS 00 0D`，**无响应码**，PAYLOAD 即 1 字节温度原值（8 位有符号） |
| `0x10` | 刷纯色（data=颜色编号） | `55 AA 00 08 10 01 00 0D`（刷白） | 先回 `0x01`，**刷屏期间持续重复 `0x01` 心跳**（`55 AA 00 08 10 01 00 0D`），刷完推 `0x02` |
| `0x11` | 刷图（data=图片槽 0~10） | `55 AA 00 08 11 01 00 0D`（刷槽 1） | 先回 `0x01`，刷屏期间持续 `0x01` 心跳，刷完推 `0x02`；**通知帧 CMD 固定写 `0x10`** |
| `0x20` | 擦除图片槽（data=槽号 0~10） | `55 AA 00 08 20 01 00 0D` | 先回 `0x01`，擦完推 `0x02`（无心跳） |
| `0x30` | 写图片分片 | `55 AA 00 F4 30 [id] 00 00 00 [233B] 00 0D` | 写响应即入队（不再回 `0x01`），每片一条 `0x02` 落盘；`0x03` 表示被丢弃、需同一 offset 重发 |

`0x30` 分片帧固定 244 字节：`55 AA 00 F4 30 [image_id] [offH offM offL] [payload 233B] 00 0D`，
offset 大端、从 0 起每片 +233；最后一片 payload 147 字节、帧长 158。172800 字节共 742 片。
写图前必须先 `0x20` 擦除同一槽。

响应码（`0x10` / `0x11` / `0x20` / `0x30` 这类带状态应答的命令使用）：`0x00` 成功、`0x01` 受理/心跳、`0x02` 完成、`0x03` 忙，`0xE0` 起为错误码。

> ⚠️ 固件 `peripheralEPDTaskCB()` 推送刷屏进度 / 完成通知时，帧里的 CMD 字段**固定写 `0x10`**，
> 所以刷图（`0x11`）的完成帧也是 `55 AA 00 08 10 02 00 0D`。`ble.js` 的 `updateImage()` 通过
> `acceptCmds: [0x10]` 同时接受两种 CMD，否则永远等不到 `0x02`。

> 整屏刷新实测可能十几秒到几十秒，所以页面用的是**空闲超时**而不是固定总超时：
> 每收到一帧同 CMD 的响应就重置计时器（刷纯色 / 刷图 20 s、擦除 60 s、每片送图 5 s），心跳不断就一直等；
> 连续这么久没有任何帧才判失败。相关逻辑见 `ble.js` 的 `sendAndWait()` / `sendFrameAndWait()`。

> ⚠️ 解析时不能一律把 PAYLOAD 首字节当响应码：`0x00` 读版本的 `10` 是版本号第一个字节、
> `0x01` 读温度的 `TS` 是原始值，都不是响应码。`readRevision()` / `readTemperature()` 单独实现，
> 拿到对应 `CMD` 的帧即视为成功。

> 存图 + 刷图链路（`0x20` 擦除 → `0x30` 写片 → `0x11` 刷图）已全通：
> `0x11` 走固件 `EPD_TaskSubmit(EPD_MDOE_IMAGE, image_id)`，槽号非法回 `0xE7`，任务队列满回 `0x03`。

## PWA（安装到桌面 / 离线打开）

三个页面共用一套 PWA 能力：

- `manifest.webmanifest`：名称、主题色、192/512 图标（含 maskable）、两个快捷方式；
- `sw.js`：Service Worker，**导航网络优先**（改完刷新就能拿到新版）、静态资源缓存优先 + 后台更新；
- `assets/js/pwa.js`：注册 SW、`beforeinstallprompt` 安装按钮、`controllerchange` 后提示「刷新缓存」。

使用方式：

| 平台 | 安装方式 |
| --- | --- |
| Chrome / Edge（桌面） | 地址栏右侧安装图标，或顶栏的「＋ 安装」按钮 |
| Android Chrome | 地址栏菜单「安装应用」，或顶栏「＋ 安装」 |
| iOS Safari | 分享 → 「添加到主屏幕」（Safari 不触发 `beforeinstallprompt`，没有安装按钮） |

离线能力：页面、样式、脚本、图标都在 `sw.js` 的 `PRECACHE` 里，断网仍能打开并做图像处理；
BLE 需要连设备，离线时只会有「不支持 Web Bluetooth」的提示。

缓存策略（v2 起）：

- **HTML 与 JS / CSS 都是网络优先**，在线时刷新即拿到最新文件；断网才回退缓存；
- 图标、manifest 这类几乎不变的内容用缓存优先 + 后台更新。

> 为什么 JS/CSS 也要网络优先：曾经用「缓存优先」，发版后会出现「HTML 是新的、脚本是旧的」，
> 典型症状就是**色板下拉空白、要刷新几次才正常**。现在只要在线就一致；万一还是遇到，
> 页面会自己亮出「⟳ 刷新缓存」按钮并提示「脚本版本过旧」。

**发版注意**：改了静态资源要把 `sw.js` 的 `VERSION` 加一（例如 `epd-toolbox-v2` → `v3`），
激活时才会清掉旧缓存；新增/删除页面或 JS/CSS 时，必须同步 `PRECACHE` 清单
（见 [docs/conventions.md](docs/conventions.md) §13）。
SW 换新版本后页面顶栏会出现「⟳ 刷新缓存」按钮，点一下即可加载新版（手机上按不出 Ctrl+F5 时用它）。

图标由脚本生成，改了设计后重跑：

```bash
node tools/make-icons.mjs   # 输出 assets/icons/*.png
```

PWA 安装要求 `https://` 或 `localhost`，`file://` 双击打开不会注册 SW。

## 本地预览

Web Bluetooth 要求安全上下文（`https://` 或 `localhost`），直接双击 `file://` 打开时只有图像处理可用。推荐起一个本地静态服务：

```bash
python -m http.server 8080
# 浏览器打开 http://localhost:8080/
```

图像处理全程在浏览器内完成，图片不会上传。

## 部署到 GitHub Pages

1. 仓库 **Settings → Pages → Source** 选择 **GitHub Actions**
2. 推送到 `main`（或 `master`）后 `.github/workflows/deploy-pages.yml` 自动部署
3. 站点地址：`https://<用户名>.github.io/<仓库名>/`

也可以在 **Actions** 页面手动 `Run workflow`。`index.html` 里的 GitHub 仓库链接是占位地址，记得替换。
