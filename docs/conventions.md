# 交互与通信约定（备忘录）

> 改页面、加命令、换设备前先过一遍这份清单。每一条都来自实际踩过的坑，
> 新增模块时按同样口径执行，不要各自发明。

## 1. 命令互斥：发出命令后禁用所有命令交互控件

**规则**：任意一条命令发出后，页面上所有命令交互空间（按钮、下拉、颜色块、参数输入）
立即禁用；只有命令**完成 / 超时 / 出错**，或连接断开后才恢复。

**为什么**：

- 固件同一时刻只接受一条命令：`EPD_TaskSubmit()` / `FlashTaskSubmitErase()` 忙时返回 `-1`，
  并发下发会被直接丢弃；
- 前端的 `sendAndWait()` 是按 `CMD` 匹配响应的，两条命令重叠会串包，
  出现「刷纯色收到擦除的完成帧」这种假成功。

**实现方式**（`assets/js/ble-console.js`）：

```js
const usable = !!client.connected && !locked;   // 连接 && 未锁定
function applyCommandEnabled() { /* 所有命令控件统一在这里开关 */ }
function setCommandLock(v) { locked = v; applyCommandEnabled(); }

busy = true; setCommandLock(true);
try { await client.xxx(); } catch (e) { ... } finally { busy = false; setCommandLock(false); }
```

**新增命令卡片时必须做**：

1. 把新增的按钮/下拉/输入加进 `applyCommandEnabled()` 的统一开关列表；
2. handler 套用上面的骨架：`busy` 守卫 → `setCommandLock(true)` → `try/catch/finally` →
   `finally` 里 `setCommandLock(false)`，**超时和异常路径也要解禁**；
3. 不要只靠 `log('上一条命令还在执行')` 这种提示——按钮还能点，就还是会误操作。

**边界**：连接 / 断开按钮不属于命令卡片，执行期间保持可用，作为卡死时的逃生通道；
断开时 `locked` 会被清掉，重连后不会一直锁着。

## 2. 长命令用「空闲超时 + 心跳保活」，不要用固定总超时

- E6 整屏刷新实测十几秒到几十秒，固定 15 s 总超时会误判失败；
- 固件在刷屏期间持续重复回 `RESPONSE_CODE_DOING`（`55 AA 00 08 10 01 00 0D`）当心跳；
- 所以 `sendAndWait()` 每收到一帧同 `CMD` 的响应就重置计时器：
  刷纯色 / 刷图 20 s、擦除 60 s 收不到任何帧才失败；
- 心跳帧不逐条写日志（几十上百条会把日志冲掉），只在第一次心跳补一条说明；
  界面用 `onHeartbeat(cmd, count)` 刷进度。

**以后加长耗时命令**：先问设备有没有心跳；没有心跳的，给足固定空闲上限并写清在提示里。

## 3. 送图（`0x30`）：先擦后写，用 ATT 写响应推进

实现见 `ble.js` 的 `writeImage()`：

- **先擦同槽**：发 `0x20` 擦除目标 `image_id`，等 `0x02` 成功才允许送图；
  擦除失败/超时直接中止，不要「擦除没回就继续写」。
- **分片固定 233 字节**：帧长 244（`55 AA 00 F4 30 [id] [offH offM offL] [payload] 00 0D`），
  offset 大端、从 0 每片 +233；最后一片 payload 147 字节、帧长 158。172800 字节 → 742 片。
- **写请求必须带响应**：`writeFrame()` 一律用 `writeValueWithResponse()`（老浏览器退回
  `writeValue()`），**不再用 `writeValueWithoutResponse()`**——固件 `fe1d988` 起 FFE3 只声明
  `GATT_PROP_WRITE`，无响应写会直接失败。连接后核对 `writeChar.properties.writeWithoutResponse`：
  为 `true` 说明设备还在跑旧固件，日志要明确提示「重新烧录后断开重连」。
  244 字节的包需要 ATT MTU ≥ 247；Web Bluetooth 没有主动请求 MTU 的接口，只能依赖系统自动协商，
  写入报长度错误时要明确提示 MTU 不足。
- **742 片不逐条写日志**：`client.silentCmd` 让该 cmd 的收发静默，进度交给进度条；
  否则日志被冲掉、页面也会卡。
- 送图期间同样 `setCommandLock(true)`，并提供「中止」（`shouldStop` 每片检查一次）。
- 送完图默认接着发 `0x11` 把这一槽刷到屏上（送图卡片「自动刷图」复选框，默认不勾）；
  只写 flash 不会显示，槽里没数据时 `0x11` 只会刷出空白。

### 3.1 分片的确认方式：ATT 写响应（成功入队不再回 `DOING`）

固件 `074fc03` 起，`0x30` 成功入队时**不再回 `DOING`**，于是「收到 `0x01` 才发下一片」的写法
会一直等下去。现在的规矩：

- **ATT 写响应 = 已入队**：`await writeFrame()` 一返回就发下一片，不要等 `DONE`；
- **`DONE`（`0x02`）只做两件事**：更新进度、确认这一片真的写进 Flash
  （`onProgress` 的 `sent` 由写响应推进，`flashed` 由 DONE 推进，界面两个百分比分别显示）；
- **收尾必须等 DONE 到齐**：最后一片的写响应只代表入队，`writeImage()` 末尾按「空闲超时」
  等所有 DONE（期间每来一条新 DONE 就续命 `idleMs`），等不到报
  「等待 Flash 落盘超时：已确认 N / M 片（可重试）」；
- **`BUSY`（`0x03`）= 队列满、这一包被丢弃**：不会再有它的 DONE，必须用**同一个 offset**
  重发（`writeImage()` 用 `acked` + `busyOffsets` 记下来，发送循环里优先重发，
  重发成功才计入 `sentCount`）；
- **`0x01` 仍要容忍**：旧固件会回 `DOING`，收到当作无事发生，不要报错；
- **错误码（`0xE0~0xE7` / `0xFF`）**：按原有逻辑直接失败、不重试（重发不会变好）；
- **速度**：逐包 `await` 写响应，7.5 ms 连接间隔理论约 31 KB/s、15 ms 约 15 KB/s；
  「每包等 DONE」只有约 7.8 KB/s，别退回去。带响应写天然串行，也不会撞
  「GATT operation already in progress」。
- **`0x20` / `0x11` 不适用本节**：它们仍是「先 `DOING` 心跳、完成推 `DONE`」的异步命令
  （`0x11` 的完成帧 CMD 见 §4）。


## 4. 刷图（`0x11`）的完成通知 CMD 是 `0x10`（固件约定）

固件 `peripheralEPDTaskCB()`（`E6_P370_CH592F/App/peripheral.c`）推送刷屏进度 / 完成通知时，
把帧里的 CMD **写死为 `CHAR3_CMD_10_UPDATE_COLOR`**，刷纯色和刷图共用同一条 8 字节通知：

```
55 AA 00 08 10 [01 心跳 | 02 完成 | FF 失败] 00 0D
```

所以等 `0x11` 的应答时**必须把 `CMD=0x10` 的帧一起算**，否则永远等不到 `0x02`：

- `ble.js` 的 `sendFrameAndWait()` 支持 `opts.acceptCmds`（额外接受的 CMD 列表），
  匹配判定为 `const accept = [cmd].concat((opts && opts.acceptCmds) || []);`；
- `updateImage(imageId, opts)` 固定带 `acceptCmds: [CMD.UPDATE_COLOR]`，外层还包了
  `withRetry()`（`0x11` 收到 `0x03` 表示任务队列满，可重试）；
- 别把这套抄给 `0x20` / `0x30`：`peripheralFlashTaskCB()` 的通知 CMD 是按操作区分的
  （擦除回 `0x20`、写片回 `0x30`），乱加接受项反而会串包；
- `acceptCmds` 只加同名通知，不要写成「接受所有 CMD」；顺带用测试把
  「无关 CMD 的完成帧不能误判成功」钉住（`tests/ble.test.mjs` 第 16 组）。

## 5. 帧解析不要假定 PAYLOAD 首字节是响应码

- `0x10` / `0x11` / `0x20` / `0x30` 的 PAYLOAD 首字节是响应码（`0x00` 成功 / `0x01` 受理·心跳 / `0x02` 完成 / `0x03` 忙 / `0xE0+` 错误）；
- `0x00` 读版本的应答**没有响应码**：`55 AA 00 0A 00 10 84 02 00 0D` 里 `10 84 02` 就是版本号，
  曾经按「首字节=响应码」解析，报出过「未知响应 0x10」；
- `parseStream()` 只负责切帧，语义交给各命令自己处理：读版本单走 `readRevision()`。

## 6. 状态显示

- 徽章只显示三态短文案：未连接 / 连接中… / 已连接；
  设备名放在同一枚徽章内部、状态词左边（`.badge-device`），不再单独排一行；
- 顶栏那一枚徽章就是唯一的状态显示，不做「滚动了才出现」的第二份（`#bleStatusTop` 已删除）；
- 命令卡片各自带一个小状态徽章：未执行 / 执行中（带耗时、心跳数）/ 成功 / 失败。

## 7. 移动端

- ≤640px：单列布局、表单项独占一行、输入框字号 ≥16px（防 iOS 聚焦放大）、
  顶栏按钮收成图标（`.btn-label` 隐藏）、表格包 `.table-wrap` 横向滚动。

## 8. 提交前自检

## 9. 命令测试页排版：卡片按命令码升序，收发日志整行置底

`ble-console.html` 的卡片顺序固定为固件命令码升序，一屏就能对上协议表：

- 第一行 `.grid-2 align-stretch`：`0x00` 读版本 / `0x10` 刷纯色；
- 第二行 `.grid-2 align-stretch`：`0x11` 刷图 / `0x20` 擦除；
- `0x30` 测试送图单独整行（参数多、还带进度条）；
- 收发日志放在所有命令卡片之后、`<footer>` 之前，整行宽度置底。

**为什么**：

- 卡片顺序就是命令码顺序，新增命令按码插到对应位置，不要「哪有空位放哪」；
- `.grid-2` 在 ≤980px 会自动塌成单列，卡片顺序 = 手机上从上往下的阅读顺序，
  所以顺序必须按命令码来，不能只靠「左右列」凑；
- 日志给整行宽度：244 字节的送图帧很长，半行宽会频繁折行，也方便对照收发顺序；
- **同一行的两张卡片必须等高**：行上加 `align-stretch`，`.grid-2.align-stretch`
  让各列撑满行高、列内 `.card` 再撑满列高，否则左右一高一矮很显眼；
- **结果区只放结论，不放原始帧**：`0x00` 卡片的结果框只显示版本号本身
  （`IC Revision：10 84 02`），完整响应帧交给底部收发日志的 rx 记录
  （`ble.js` 的 `onNotify` 已经逐帧 `log('rx', …)`，不用在卡片里再抄一遍）。

**新增命令卡片时**：

1. 按命令码找到插入位置，沿用 `0x11` 卡片的写法（`.col` 分列 + 独立槽位下拉）；
2. 标题统一 `0xNN · 中文名`，`.sub` 写固件枚举名（如 `CHAR3_CMD_11_UPDATE_IMAGE`）；
3. 新增控件挂进 `el` 映射与 `applyCommandEnabled()`（见 §1），别只改 HTML；
4. **卡片上方写注释块**（`<!-- ============ 0xNN · 中文名 ============`），
   逐条写清：完整帧格式（含帧长与实际取值，如 `55 AA 00 08 11 [image_id] [CRC] 0D`）、
   同步还是异步（异步要写清 0x01 心跳 / 0x02 完成 / CMD 是否与命令码一致）、
   依赖的控件 id、容易踩的固件 quirk（如 §4 的通知 CMD 固定 0x10）。
   注释是给「半年后回来改这块的人」看的，光写「刷图卡片」没有意义；
   对应 JS handler 的小节标题下也补一行同口径的说明，让 HTML 与 JS 两边对得上。

## 10. 提交约定：每次修改都要提交，一条 commit 讲清一件事

- **每次改动都要落到 commit**，不要攒一堆改动留在工作区；
- **一条 commit 只讲一件事**：加命令、调布局、改文案、补测试分开放；
  一次改动涉及多个关注点时，拆成多条 commit，而不是塞成一条大提交；
- **message 要写详细**：标题一句话概括并带前缀（`feat(ble): …` /
  `refactor(ble-console): …` / `docs: …`），正文分点写「改了什么」和「为什么这么改」；
  关键取舍（比如为什么在前端用 `acceptCmds` 兼容固件的 CMD quirk，而不是改固件）
  必须写进正文，否则几个月后没人知道当初为什么这么选；
- 提交前按 §8 跑自检：语法、测试、HTML 配平不过就不要提交。

## 11. 图像转换页的送图 / 刷图：两个按钮，一个槽位

`e6-image.html` 的「4 · 送图 / 刷图」卡片复用 `assets/js/ble.js`，不再手写组帧 / 拆帧：

- **脚本顺序固定** `e6-codec.js` → `ble.js` → `e6-page.js`，`ble.js` 暴露 `window.EPDBLE`；
  组帧、分片、空闲超时、心跳、重试全部交给它，页面只负责取 `state.result.bytes` 和画进度；
- **送图（`0x30`）与刷图（`0x11`）是两个按钮、共用一个槽位下拉**（`#slotSelect`）：
  送图 = `0x20` 擦除该槽 + 742 片 `0x30`（只落盘，屏上不变），刷图 = `0x11` 把该槽已有的图显示出来。
  一个下拉就够——用户想的就是「这台设备上的第几格」，分成两个下拉只会诱导选错；
- **送图按钮受尺寸约束**：转换结果必须正好 172800 字节（480 × 720 4bpp）才可点，
  否则禁用并保留说明（其它分辨率只能导出，写进 Flash 会错位）；
- **送图成功后可以自动刷图**：`#refreshAfter` 复选框默认不勾（有人只想先把图存进 Flash），
  位置在「中止」按钮右边、文案就叫「自动刷图」；勾上时 `writeImage()` 返回后接着
  `await client.updateImage(slot)`；**刷图失败要单独报**：此时 742 片已经写好，catch 里用 `uploaded`
  标记区分为「送图成功但刷图失败」，绝不能报成「送图失败」，否则用户会白重送一遍；
- **送图卡片的版面**：状态 `#sendState` 与耗时 `#sendMs` 放卡片标题右侧，
  下面一行是槽位下拉 + 送图 / 刷图 / 中止 + 自动刷图勾选框，**最底下只有进度条 `#sendBar` 和速度
  `#sendSpeed`**——不放帧预览行、不放提示段落，片号 / 重试 / 完成字节数一律写进「5 · 日志」；
- **按钮文案只写命令名**（`送图` / `刷图`），命令码写在标题的 `.sub` 里（`4 · 送图 / 刷图 0x30 · 0x11`），
  按钮保持短、不被括号里的 `0x30` 撑宽；
- **连接 / 断开与连接状态徽章放顶部工具条，不塞进命令卡片**（和 `ble-console.html` 一致）：
  送图要几十秒，用户常常滚到下面看进度，连接入口跟着页面滚走就得来回找；
  顶栏里依次是 `#bleState`（内含设备名 `#bleDeviceName` + 状态词 `#bleStateText`）、`#btnConnect`、`#btnDisconnect`；
- **设备名放进状态徽章内部、在状态词左边**（`.badge-device`）：`已连接 · EPD-E6-01`
  这类写法只占一处，比顶栏再排一个独立 `<span>` 更省宽度；设备名过长省略、≤640px 隐藏（只留状态词），
  避免徽章把连接按钮挤到第二行；
- **设备名过滤输入框 `#nameFilter` 放页面标题右侧**（`.page-head-row` + `.title-filter`，紧贴 `h1`）：
  不占顶栏宽度（顶栏还要放徽章和两个按钮），标题常驻可见，也不会跟 `← 工具箱` 挤在一起；
  默认 `EPD`，留空则列出全部设备，连接时把值作为 `namePrefix` 传给 `client.connect()`；
  它只是过滤，不算命令控件，所以不进 `applyCommandEnabled()` 的互斥集合，
  窄屏（≤640px）用 `.title-filter { display: none; }` 收起，退回「列出全部设备」；
  两个页面（`e6-image.html` / `ble-console.html`）用同一套 DOM 与类名，不要各自发挥；
- `ble-console.html` 里不再单独用一张卡片放名称过滤框和连接状态：
  连接按钮、状态徽章都已在顶栏，卡片只保留折叠的「高级：自定义服务 / 特征 UUID」；
- 互斥、状态徽章、进度与中止沿用 §1 / §6 的同一套写法（`applyCommandEnabled()` /
  `setCommandLock()` / `setSendState()`），命令执行中除连接外的控件全部禁用。

## 12. 面板方向：只在打包输出时上下翻转

- 这块面板装反了：屏上看到的画面相对原图**上下颠倒**（左右方向是对的），
  所以 `e6-image.html` 的「上下翻转」勾选框（`#flipV`）**默认勾选**，
  但翻转只发生在**输出数据**这一步：`dither()` 之后、`pack()` 之前，
  用 `Codec.flipVIds()` 把量化后的色号上下翻一次，打包格式（列优先、高半字节在上）不变；
- **预览（原图 + 抖动结果）一律正常方向**：用户看到的就是自己选的图和抖动效果，
  否则会以为图被处理坏了。`state.srcImageData` 与 `state.result.imageData` 都是未翻转的，
  翻转后的色号只进 `state.result.ids` / `state.result.bytes`——
  也就是导出的 `.bin` / `.h`、复制的 hex、以及送图真正发出去的字节；
- 翻转作用在**量化后的色号**上（纯行序重排 `(x, y) → (x, h-1-y)`），
  不是对源图像素重采样、更不是 canvas 旋转：不会引入半像素采样，也不会改变颜色判定；
- **补偿放在页面这一层，不要写死在 `e6-codec.js` 的 `pack()` 里**：换一块装法不同的屏、
  或者只是想导出给别的固件用，都得能一键关掉；
- 测试要钉住三件事：只换行不换列、两次翻转回原数组、打包结果是每列高/低半字节互换
  （`03 15 → 30 51`），并额外确认抖动结果本身仍在正常方向；
- 勾选状态变化要触发自动重算（`scheduleAuto()`），并往日志里写一句当前行为，方便排查。
